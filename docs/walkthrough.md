# Contest System: how it is built and how every endpoint behaves

This is the long-form companion to the README. The first half explains what the system is, which pieces it is made of and why each one is there. The second half is a log of every endpoint being called against a running server, with the real request and response and a short note on what happened inside. That second half is generated by `scripts/record-api.mjs`, so it is never out of date with the code.

Related documents: `README.md` (setup and API reference), `PLAN.md` (design decisions before writing code), `AI_USAGE.md` (the AI parts in depth), `docs/schema.sql` (database dump).

## 1. What the system does

A JSON API for programming quiz contests.

- Admins create contests, write questions or have them generated, and manage roles.
- Users register, join contests that are running, answer once, and get a score and rank immediately.
- VIP users can additionally enter VIP-only contests.
- Guests can browse contests and leaderboards and use the natural-language search without an account.
- When a contest ends, a background worker closes it, picks the winner and records the prize.
- Everyone sees their own history, the contests they joined but have not finished, and the prizes they won.

Requirement from the brief, and where it lives:

| requirement | where |
|---|---|
| roles admin / VIP / normal / guest | `middleware/auth.ts`, `services/contests.ts` (`canParticipate`) |
| VIP vs normal contests | `contests.access_level`, checked in `assertCanParticipate` |
| single-select, multi-select, true/false questions | `schemas/question.ts`, `services/scoring.ts` |
| scoring and leaderboard | `services/scoring.ts`, `controllers/leaderboard.ts` |
| prizes | `services/finalize.ts`, `prizes` table |
| user history including in-progress | `controllers/me.ts` |
| natural-language contest search | `services/search.ts`, `ai/` |
| AI question generation for admins | `controllers/questions.ts` (`generate`), `ai/` |
| auth, validation, error handling | `middleware/` |
| rate limiting | `middleware/rateLimit.ts` |
| concurrency safety | unique constraints, row locks, advisory lock (section 7) |
| structured logging | pino, `logger.ts`, `app.ts` |
| migrations, dump, Postman | `migrations/`, `docs/schema.sql`, `postman/` |

## 2. Stack, and why each piece

| piece | role | why this one |
|---|---|---|
| Node.js 22 + TypeScript | runtime and language | types on every row and request body catch a whole class of mistakes before the tests run; `tsx` runs TS directly in development, `tsc` builds plain JS for production |
| Express 4 | HTTP framework | small, well known, easy to reason about middleware order. Version 4 does not forward rejected promises, so controllers are wrapped by a tiny `asyncHandler` |
| PostgreSQL 16 | database | relational data with real constraints: enums, `check`, `unique`, foreign keys with cascade. Also gives full-text search, window functions, row locks and advisory locks, all of which the system uses |
| knex | migrations and query builder | SQL stays visible (`select ... for update`, `rank() over (...)`, `on conflict`) instead of hidden behind an ORM; migrations and seeds are plain files |
| zod 4 | validation | one schema per request shape, inferred TypeScript types, and the same schema validates model output for generated questions |
| jsonwebtoken + bcryptjs | auth | stateless tokens with `{ sub, role }`, passwords hashed with bcrypt cost 10 |
| pino + pino-http | logging | JSON logs with a request id on every line; fast; pretty-printed only in development |
| express-rate-limit 8 | rate limiting | three limiters with different keys and windows; standard `RateLimit` headers |
| @anthropic-ai/sdk | AI provider | structured output (`messages.parse` with a zod schema) so the model returns JSON that already matches the schema; typed errors for clean mapping |
| vitest + supertest | tests | 22 tests run the real Express app against a real PostgreSQL database, no mocks for the database |
| prettier | formatting | one style, enforced with `npm run format:check` |

## 3. How a request travels

```
client
  → express.json (200 kb limit)
  → pino-http       assigns or reuses X-Request-Id, logs every response
  → generalLimiter  300 requests / 15 min per user or IP
  → router          one file per resource in src/routes
      → auth middleware     optionalAuth | requireAuth | requireRole('admin')
      → validate(schema)    zod: body is replaced by the parsed value, query/params go to res.locals
      → controller          plain async (req, res) function in src/controllers
          → service         business rules and queries in src/services
              → knex → PostgreSQL
  → errorHandler    every thrown error becomes { error: { code, message, details } }
```

Folder layout:

```
src/
  app.ts            express app: logging, limits, /api router, error handler
  server.ts         listen, start the finalizer worker, graceful shutdown
  config.ts         environment parsing with defaults
  routes/           routers: middleware + schema + controller per endpoint
  controllers/      request handlers
  schemas/          zod request schemas
  services/         contests, questions, scoring, finalize, search
  middleware/       auth, validate, errors, rateLimit, asyncHandler
  ai/               provider interface, Anthropic and mock implementations, question bank
migrations/ seeds/  knex
tests/              vitest + supertest
postman/            collections (by feature, by role) + environment
scripts/            record-api.mjs (generates the second half of this file)
```

Why this split: routers show the whole surface of a resource on one screen (who may call it, what is validated, what runs). Controllers only translate HTTP into service calls and back. Services hold the rules and can be tested or reused without HTTP (the finalizer worker uses them directly).

## 4. Data model

Six tables, created by one knex migration (`migrations/20261021090000_init.js`).

| table | key columns | notes |
|---|---|---|
| `users` | `id` uuid, `email` unique, `password_hash`, `role` enum `user_role` | new rows are `user` |
| `contests` | `name`, `description`, `access_level` enum, `difficulty` enum, `tags text[]`, `prize` nullable, `start_time`, `end_time`, `finalized_at`, `winner_user_id`, `created_by` | `check (end_time > start_time)`; generated `search_vector tsvector` with a GIN index; GIN index on `tags`; index on `(start_time, end_time)` |
| `questions` | `contest_id`, `position`, `type` enum, `text`, `options jsonb`, `correct_answers jsonb`, `explanation`, `points` | `check (points > 0)`, `unique (contest_id, position)`, cascade on contest delete |
| `participations` | `contest_id`, `user_id`, `joined_at`, `submitted_at`, `score` | `unique (contest_id, user_id)`; partial index `(contest_id, score desc, submitted_at asc) where submitted_at is not null` for leaderboards |
| `answers` | `participation_id`, `question_id`, `selected jsonb`, `is_correct` | `unique (participation_id, question_id)` |
| `prizes` | `contest_id` unique, `user_id`, `prize`, `awarded_at` | one prize per contest |

Decisions worth knowing:

- **Status is computed, not stored.** `upcoming`, `active`, `ended` come from `start_time`, `end_time` and the current time. Nothing can drift and no job has to flip a status column.
- **Enums in PostgreSQL** for roles, access level, difficulty and question type. Bad values fail at the database as well as in zod.
- **`search_vector` is a generated column**: `to_tsvector('english', name || ' ' || description) || array_to_tsvector(tags)`. It updates itself on every write and the GIN index makes `q=` searches cheap. `array_to_tsvector` is used because `array_to_string` is not immutable and cannot appear in a generated column.
- **Options and answers are `jsonb`** because a question's options are a small ordered list that is always read as a whole.
- **Partial index for leaderboards** only covers rows that were submitted, which is exactly what ranking queries read.

## 5. Roles and what each may do

| | guest | user | vip | admin |
|---|---|---|---|---|
| list and view contests, leaderboards, search | yes | yes | yes | yes |
| join and submit normal contests | no | yes | yes | yes |
| join and submit VIP contests | no | no | yes | yes |
| see a contest's questions | no | after joining, without answers | after joining, without answers | always, with answers |
| own history, in-progress, prizes | no | yes | yes | yes |
| create, edit, delete contests and questions, generate questions, change roles, finalize | no | no | no | yes |

Implementation: `optionalAuth` lets guests through and attaches `req.user` when a valid token is present. `requireAuth` demands a user. `requireRole('admin')` demands a role. `canParticipate(user, contest)` is the one function that knows VIP contests need `vip` or `admin`; it is used both for the `can_participate` flag in responses and for the `403 VIP_ONLY` check on join.

## 6. Contest lifecycle, scoring, ranking

1. Admin creates the contest with a time window and adds questions (by hand or generated).
2. While `active`, users join. One participation per user per contest.
3. A participant submits once. Scoring (`services/scoring.ts`):
   - a question is correct only if the selected set equals the correct set; for multi-select a partial match is wrong;
   - a correct question adds its `points` (default 1, admins can set more; generated advanced questions get 2);
   - wrong or unanswered questions add 0, nothing is ever subtracted;
   - the response carries `score`, `maxScore`, `correctCount` and the current `rank`.
4. Ranking is `rank() over (order by score desc, submitted_at asc)`: higher score first, earlier submission wins ties, equal rows share a rank.
5. When `end_time` passes, the finalizer sets `finalized_at`, stores `winner_user_id` (top of the ranking) and inserts a `prizes` row if the contest has a prize. Contests with no submissions are finalized without a winner.
6. History shows every finished contest with score, rank and `won`; in-progress shows joined-but-unsubmitted contests with `missed: true` once they have ended.

## 7. Concurrency: the three places it matters

- **Double join.** `insert ... on conflict (contest_id, user_id) do nothing returning *`. Two simultaneous joins both succeed from the client's point of view: the first gets `201`, the second gets `200` with the existing row. The unique constraint is what makes this safe, not application logic.
- **Double submit.** The submit runs in a transaction and reads the participation with `select ... for update`. A second concurrent submit blocks on the row lock, then sees `submitted_at` already set and fails with `409 ALREADY_SUBMITTED`. Verified by a test that fires five submits at once and expects exactly one `200`.
- **Finalizer on several instances.** `finalizeDueContests` takes `pg_try_advisory_xact_lock(hashtext('contest-finalizer'))`; if another instance holds it, this run does nothing. Inside, `finalizeContest` does `update contests set finalized_at = now() where id = ? and finalized_at is null and end_time <= now() returning *`, so even two direct calls can only have one winner. The test runs two finalizations in parallel and checks that one prize exists.

Rate limiting and the search cache are per process. For several replicas, the limiter store would move to Redis (`rate-limit-redis`) and the cache would move with it. Both are noted in the code.

## 8. Authentication

- `POST /api/auth/register` creates a `user` and returns a token immediately. `POST /api/auth/login` returns a token. Both are behind the auth limiter (20 per 15 minutes per IP).
- The token is a JWT signed with `JWT_SECRET`, payload `{ sub: userId, role }`, expiry `JWT_EXPIRES_IN` (default one day).
- The role is read from the token on every request. That makes role checks free (no database read), and it means a promotion takes effect at the next login. `GET /api/auth/me` does read the database, so a deleted account is detected.
- Passwords are hashed with bcrypt (cost 10) and never leave the server; the `password_hash` column is stripped from every response.
- A wrong email and a wrong password produce the same `401 BAD_CREDENTIALS`.

## 9. Validation and errors

Every request shape has a zod schema in `src/schemas`. The `validate` middleware parses the body, query or params, replaces the body with the parsed (and defaulted) value, and turns failures into `400 VALIDATION_ERROR` with `details: [{ field, message }]`. Field paths point into arrays (`questions.1.options`).

All errors share one shape:

```json
{ "error": { "code": "VIP_ONLY", "message": "This contest is only open to VIP users", "details": null } }
```

| status | code | when |
|---|---|---|
| 400 | `VALIDATION_ERROR` | body, query or params failed the schema |
| 400 | `INVALID_JSON` | body is not valid JSON |
| 400 | `BAD_REQUEST` | PostgreSQL rejected a value (error 22P02) |
| 400 | `UNKNOWN_QUESTION`, `DUPLICATE_ANSWER`, `INVALID_OPTION` | bad answers in a submission |
| 401 | `UNAUTHENTICATED` | no token on a protected route |
| 401 | `INVALID_TOKEN` | malformed or expired token, or the user no longer exists |
| 401 | `BAD_CREDENTIALS` | login failed |
| 403 | `FORBIDDEN` | role too low (admin routes) |
| 403 | `VIP_ONLY` | normal user joining a VIP contest |
| 403 / 404 / 409 | `NOT_JOINED` | reading questions (forbidden), reading a result (nothing there yet), submitting (conflicts with the state) without having joined |
| 404 | `CONTEST_NOT_FOUND`, `USER_NOT_FOUND`, `NOT_FOUND` | missing contest, user, or route |
| 409 | `EMAIL_TAKEN`, `CONFLICT` | duplicate email; any other unique violation (23505) |
| 409 | `CONTEST_NOT_ACTIVE`, `ALREADY_SUBMITTED`, `NO_QUESTIONS` | joining or submitting at the wrong time or twice |
| 409 | `CONTEST_NOT_ENDED`, `ALREADY_FINALIZED` | finalizing too early or twice |
| 422 | `AI_REFUSED` | the model declined the request |
| 429 | `RATE_LIMITED` | any limiter |
| 500 | `AI_MISCONFIGURED` | provider credentials invalid |
| 500 | `INTERNAL` | anything unexpected; the response carries `requestId` so the log line can be found |
| 502 | `AI_UNAVAILABLE`, `AI_BAD_OUTPUT` | provider error; model output failed validation |
| 503 | `AI_RATE_LIMITED` | the provider is rate limiting us |

The error handler is the last middleware. `AppError` instances are returned as they are (5xx ones are logged), `SyntaxError` from the JSON parser becomes `INVALID_JSON`, PostgreSQL error codes 23505 and 22P02 are mapped, and everything else is logged with the request id and returned as `500 INTERNAL`.

## 10. Rate limiting

| limiter | applies to | limit | key |
|---|---|---|---|
| general | every `/api` route | 300 per 15 minutes | user id when signed in, else IP |
| auth | register, login | 20 per 15 minutes | IP |
| ai | search, question generation | 10 per minute | user id when signed in, else IP |

All limits are environment variables. Responses carry `RateLimit` and `RateLimit-Policy` headers (draft 8); a blocked request gets `429 RATE_LIMITED`. The AI limiter sits before the search cache on purpose: the limit protects the endpoint, not only the model bill.

## 11. Logging

pino writes one JSON line per event. pino-http logs every request with method, url, status, response time and a request id (taken from `X-Request-Id` if the client sends one, otherwise a UUID). Log level follows the status: `info` for 2xx and 3xx, `warn` for 4xx, `error` for 5xx. Business events are logged with context: `user registered`, `failed login`, `contest created`, `questions generated` (with provider, counts and topic), `answers submitted` (score), `contest finalized` (winner and prize), `nl search` (filters, cache hit). In development the output is pretty-printed; in tests the level is `silent`.

## 12. The AI parts

Two features call a model, both behind the same two-method interface (`AiProvider`): `parseSearch(sentence)` returns filters, `generateQuestions(params)` returns questions. Two implementations:

- `AnthropicProvider`: Claude through the official SDK with structured output. The zod schema is passed as the output format, so the reply is parsed JSON that already matches the schema. Model from `AI_MODEL` (default `claude-opus-5-5`). SDK errors are mapped to the `AI_*` codes above.
- `MockProvider`: used by the tests and whenever there is no `ANTHROPIC_API_KEY`. Search uses keyword rules. Generation draws from a hand-written bank of real questions (`ai/questionBank.ts`) for JavaScript, Node.js, TypeScript, SQL and Python, picked by the requested types with the requested difficulty first; other topics get general programming questions. Responses say `provider: "mock"`, so nobody mistakes them for model output.

**Search pipeline.** Sentence → (cache lookup by normalised text, 10 minutes, 500 entries) → provider returns `{ status, accessLevel, difficulty, topics, hasPrize, startsWithinDays }` with `null` for anything the sentence did not say → the same `applyFilters` as the list endpoint runs the SQL → if topics matched no tag, fall back to full-text search on name and description (`relaxed: true`). The model never touches data; it only interprets the sentence.

**Generation pipeline.** Admin sends topic, difficulty, count (1 to 20), question types and `save` → provider returns questions → each one is converted to the hand-written shape and run through the *same* question schema admins use → invalid ones are dropped and counted as `rejected` → with `save: true` the survivors are inserted in a transaction with continuing positions and the response is `201`; with `save: false` they are returned for review with `200`. If nothing survives, `502 AI_BAD_OUTPUT` and nothing is written.

Guardrails: admin only for generation, rate limited, input validated before any call, output validated after, user text never placed in the system prompt, no user records sent to the model, every call logged with latency and token counts.

## 15. Trade-offs and what would come next

- In-memory rate limiter and search cache: fine for one instance, Redis for several. The database-level guards (unique constraints, row locks, advisory lock) already work across instances.
- JWT without refresh tokens: a one-day expiry keeps it simple; a refresh flow or a token revocation list would be the next step for a real product.
- Offset pagination: simple and enough for these sizes; keyset pagination for very long leaderboards.
- The mock question bank is a demo stand-in, not a substitute for the model. With credit on the key the Anthropic provider takes over without any code change.
- No per-question time limits or contest-wide timers; all answers are submitted in one request.

### Auth and roles

Registration always creates a `user`. Login returns a JWT whose payload is `{ sub, role }`; the role check on every later request reads the token, not the database, so a promotion needs a fresh login.

#### 2. Register a new user

`POST /auth/register` with no token

Request body:
```json
{
  "name": "Walkthrough User",
  "email": "walk-user-1792644924022@example.com",
  "password": "password123"
}
```

Response `201 Created`:
```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "user": {
    "id": "e0cd21ba-ff84-452b-bfd5-0574a7a47e97",
    "name": "Walkthrough User",
    "email": "walk-user-1792644924022@example.com",
    "role": "user",
    "created_at": "2026-10-22T04:55:25.536Z"
  }
}
```

A token comes back straight away, so the client does not need a second login call. The password is stored as a bcrypt hash (cost 10) and never returned.

#### 3. Register with the same email again

`POST /auth/register` with no token

Request body:
```json

  "name": "Walkthrough User",
```

### Rate limiting

Three limiters from `express-rate-limit`: general (300 per 15 minutes per user or IP), auth (20 per 15 minutes per IP on register and login) and AI (10 per minute per user or IP on search and generation). All answer `429 RATE_LIMITED` with standard `RateLimit` headers.

Twelve different searches by the same user within a minute → statuses `200, 200, 200, 200, 200, 200, 200, 200, 200, 200, 429, 429`.

#### 58. The 11th search in a minute

`GET /contests/search?q=rate limit probe 10` as user

Response `429 Too Many Requests`:
```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "Too many requests, slow down"
  }
}
```

Headers: `RateLimit: "300-in-15min"; r=217; t=864, "10-in-1min"; r=0; t=60`, `RateLimit-Policy: "300-in-15min"; q=300; w=900; pk=:YmIwY2Q1MTM2YWU1:, "10-in-1min"; q=10; w=60; pk=:MzFmZTc5MDkyMmMz:`. The limiter runs before validation and before the cache, so cached queries count too.
