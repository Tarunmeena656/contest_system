# Contest System

A backend for running quiz contests. Admins create contests and questions (by hand or generated by AI), users join contests, answer, get scored, and climb a leaderboard. The top scorer gets the prize when the contest closes. Users can search contests in plain English.

Node.js + TypeScript + Express + PostgreSQL. No frontend; everything is a JSON API with a Postman collection in `postman/`.

Related docs: [PLAN.md](PLAN.md) (approach and architecture), [AI_USAGE.md](AI_USAGE.md) (how and where AI is used).

## Quick start

Requirements: Node 20+, PostgreSQL 13+ (for `gen_random_uuid`).

```bash
npm install
cp .env.example .env            # set DATABASE_URL and JWT_SECRET; ANTHROPIC_API_KEY is optional
createdb contests
npm run migrate                 # knex migrations in migrations/
npm run seed                    # 3 users, 4 contests, questions
npm run dev                     # http://localhost:3000
```

Without an `ANTHROPIC_API_KEY` the AI features run on a deterministic mock provider, so everything still works offline (`AI_PROVIDER=mock`). The mock answers searches with keyword rules and generates questions from a small built-in bank for JavaScript, Node.js, TypeScript, SQL and Python; other topics get general programming questions. Responses carry `provider: "mock"` so nobody mistakes them for model output.

Seeded logins (password after the slash):

| role | email | password |
|---|---|---|
| admin | admin@contest.dev | Admin123! |
| vip | vip@contest.dev | Vip12345! |
| user | user@contest.dev | User1234! |

Tests need a second database:

```bash
createdb contests_test          # .env.test points at it
npm test                        # 22 tests: auth, access rules, scoring, concurrency, leaderboard, prizes, AI
```

Other scripts: `npm run build` / `npm start` (compiled), `npm run typecheck`, `npm run migrate:rollback`, `npm run db:reset` (rollback, migrate, seed).

## Roles and access

| | guest | user (signed in) | vip | admin |
|---|---|---|---|---|
| list / view contests, leaderboards | yes | yes | yes | yes |
| join and submit normal contests | no | yes | yes | yes |
| join and submit VIP contests | no | no | yes | yes |
| see questions of a contest | no | after joining | after joining | always, with answers |
| history, in-progress, prizes | no | own | own | own |
| natural-language search | yes | yes | yes | yes |
| create / edit / delete contests and questions, generate questions, change roles, finalize | no | no | no | yes |

New registrations are `user`. An admin promotes with `PATCH /api/users/:id/role`.

## Contest lifecycle

`start_time` and `end_time` decide the status: `upcoming`, `active`, `ended`. Joining and submitting are only allowed while active. Each user has one participation per contest and can submit once. Score = sum of `points` of fully correct questions (default 1 point each; multi-select must match the exact set, a partial match is wrong, an unanswered question is wrong). Wrong answers never subtract.

When a contest ends, the finalizer (runs every `FINALIZER_INTERVAL_MS`, or `POST /api/contests/:id/finalize` by an admin) picks the winner: highest score, earliest submission on ties. If the contest has a `prize`, a prize record is written for the winner. Finalization is idempotent and safe with several app instances (see PLAN.md).

## API

Base URL `http://localhost:3000/api`. Send `Authorization: Bearer <token>` where auth is required. Errors always look like:

```json
{ "error": { "code": "VIP_ONLY", "message": "This contest is only open to VIP users", "details": null } }
```

Validation errors use code `VALIDATION_ERROR` with `details: [{ field, message }]`. Rate limiting answers `429` with code `RATE_LIMITED` and standard `RateLimit-*` headers. Every response carries the request id in logs; unknown errors return it in the body as `requestId`.

List endpoints take `page` (1-based) and `pageSize` (max 100) and return `{ items, total, page, pageSize }`.

### Auth

| method | path | auth | body / notes |
|---|---|---|---|
| POST | `/auth/register` | | `{ name, email, password (8+) }` → `201 { token, user }` |
| POST | `/auth/login` | | `{ email, password }` → `{ token, user }` |
| GET | `/auth/me` | any | current user |
| PATCH | `/users/:id/role` | admin | `{ role: "user" \| "vip" \| "admin" }` |

### Contests

| method | path | auth | body / notes |
|---|---|---|---|
| GET | `/contests` | optional | filters: `status=upcoming\|active\|ended`, `access=normal\|vip`, `difficulty=beginner\|intermediate\|advanced`, `tag=node.js`, `q=full text`, `page`, `pageSize`. Each item has `status` and `can_participate` for the caller |
| POST | `/contests` | admin | `{ name, description?, access_level?, difficulty?, tags?: string[], prize?: string\|null, start_time, end_time }` |
| GET | `/contests/:id` | optional | plus `question_count`, `participant_count`, `my_participation` |
| PATCH | `/contests/:id` | admin | any subset of the create body |
| DELETE | `/contests/:id` | admin | cascades to questions, participations, prizes |
| GET | `/contests/search?q=...` | optional | natural-language search, see below |

### Questions

| method | path | auth | body / notes |
|---|---|---|---|
| POST | `/contests/:id/questions` | admin | `{ questions: [ { type, text, options[], correct_answers[], explanation?, points? } ] }` (up to 50) |
| GET | `/contests/:id/questions` | joined user / admin | participants get questions without `correct_answers` and `explanation` |
| POST | `/contests/:id/questions/generate` | admin | AI generation, see below |

Question rules, enforced on input: `single-select` has exactly one correct answer; `multi-select` has one or more; `true-false` has options exactly `["True", "False"]`. Options must be unique and every correct answer must be one of the options.

### Participation

| method | path | auth | body / notes |
|---|---|---|---|
| POST | `/contests/:id/join` | user/vip/admin | `201` on first join, `200` with the existing participation after that. `403 VIP_ONLY`, `409 CONTEST_NOT_ACTIVE` |
| POST | `/contests/:id/submit` | user/vip/admin | `{ answers: [ { questionId, selected: string[] } ] }` → `{ score, maxScore, correctCount, totalQuestions, rank, submittedAt }`. One submission per user: `409 ALREADY_SUBMITTED`. Questions left out score 0 |
| GET | `/contests/:id/result` | joined user | own answers with correctness, correct answers and explanations (after submitting) |

### Leaderboards, history, prizes

| method | path | auth | notes |
|---|---|---|---|
| GET | `/contests/:id/leaderboard` | optional | ranked participants (`rank` has gaps on ties, earlier submission wins), plus `me` when logged in |
| GET | `/leaderboard` | optional | overall: total score across contests, contests played, prizes won |
| GET | `/me/history` | user | finished contests with score, rank, `won` |
| GET | `/me/in-progress` | user | joined but not submitted; `missed: true` if the contest already ended |
| GET | `/me/prizes` | user | prizes won |
| POST | `/contests/:id/finalize` | admin | close an ended contest now instead of waiting for the worker |

### Natural-language search

`GET /api/contests/search?q=Show me active VIP contests`

The sentence is turned into a small set of filters by the AI provider, and the filters run as a normal SQL query. The response includes the interpretation so clients can show "searched for: active, vip":

```json
{
  "query": "Show me active VIP contests",
  "filters": { "status": "active", "accessLevel": "vip", "difficulty": null, "topics": [], "hasPrize": null, "startsWithinDays": null },
  "cached": false,
  "relaxed": false,
  "items": [ ...contests... ],
  "total": 1, "page": 1, "pageSize": 20
}
```

Supported capabilities:

| in the sentence | becomes |
|---|---|
| active / ongoing / currently running, upcoming / starting soon, past / finished | `status` |
| VIP, normal / regular | `accessLevel` |
| beginner / easy, intermediate / medium, advanced / hard / difficult | `difficulty` |
| technology or subject names (JavaScript, Node.js, backend, SQL ...) | `topics`, matched against contest tags, falling back to full-text search on name and description (`relaxed: true`) |
| with prizes / rewards | `hasPrize` |
| today, this week, this month | `startsWithinDays` (1 / 7 / 30) together with `status: upcoming` |

Not supported: sorting or ordering requests, numeric comparisons ("more than 10 questions"), negations ("not about Java"), and anything about other users. Those words are ignored. Interpretations are cached for 10 minutes per normalised query, and the endpoint is rate limited (`RATE_LIMIT_AI_MAX` per minute). The mock provider handles the example queries from the brief with keyword rules; the real provider handles free phrasing.

### AI question generation

`POST /api/contests/:id/questions/generate` (admin)

```json
{
  "topic": "JavaScript",
  "difficulty": "medium",
  "count": 5,
  "questionTypes": ["single-select", "multi-select", "true-false"],
  "save": true
}
```

`difficulty` accepts `easy|medium|hard` or `beginner|intermediate|advanced`; `count` is 1..20; `questionTypes` defaults to all three; `save: false` returns a preview without writing anything.

Response (`201` when saved, `200` for a preview):

```json
{
  "provider": "anthropic",
  "requested": 5,
  "generated": 5,
  "rejected": 0,
  "saved": true,
  "questions": [
    {
      "id": "…", "contest_id": "…", "position": 1,
      "type": "multi-select",
      "text": "Which of the following are valid JavaScript data types?",
      "options": ["String", "Number", "Boolean", "Float"],
      "correct_answers": ["String", "Number", "Boolean"],
      "explanation": "String, Number and Boolean are JavaScript data types.",
      "points": 1
    }
  ]
}
```

Generated questions go through the same validation as hand-written ones; anything malformed is dropped and counted in `rejected`. Advanced questions are worth 2 points, the rest 1.

## Postman

Two collections, pick whichever reads better:

- `postman/contest-system.postman_collection.json` is grouped by feature. Import it with `postman/local.postman_environment.json` and run the folders top to bottom: the login requests store tokens in the environment, "Create contest" stores `contestId`, "Get questions" stores the question ids used by "Submit answers".
- `postman/by-role.postman_collection.json` is grouped by role: one folder each for guest, normal user, VIP and admin, with the refused actions included (a user joining a VIP contest, a VIP adding questions, and so on). It needs no environment; folder 0 signs in as every role and stores the tokens as collection variables. Every request has a status assertion, so it also runs green in the Collection Runner or `newman run postman/by-role.postman_collection.json`.

Both need the seed data (`npm run seed`).

## Database

Schema lives in `migrations/` (knex) and a plain SQL dump is in `docs/schema.sql`. Tables: `users`, `contests`, `questions`, `participations`, `answers`, `prizes`. Notable bits: Postgres enums for roles, access level, difficulty and question type; a generated `tsvector` column with a GIN index for full-text search; a partial index on `(contest_id, score desc, submitted_at asc)` that backs the leaderboard; `unique (contest_id, user_id)` on participations.

## Project layout

```
src/
  app.ts              express app: logging, rate limits, error handler
  server.ts           http server + finalizer worker + graceful shutdown
  config.ts           env parsing
  routes/             one router per resource: middleware + schema + controller per endpoint; index.ts mounts them under /api
  controllers/        request handlers: auth, users, contests, questions, participation, leaderboard, me, search
  schemas/            zod request schemas (body, query, params) used by the validate middleware
  services/           business logic and queries: contests (status, access rules, filters), questions, scoring, finalize, search
  middleware/         auth (jwt, roles), validate (zod), errors, rateLimit, asyncHandler
  ai/                 provider interface, anthropic + mock implementations, output schemas
migrations/ seeds/    knex
tests/                vitest + supertest against a real postgres
postman/              collections (by feature, by role) + environment
docs/schema.sql       pg_dump of the schema
docs/walkthrough.md   how it is built + every endpoint with a recorded request and response
scripts/record-api.mjs regenerates the recorded part of the walkthrough
```

A request goes router → `validate(schema)` → controller → service. Controllers are plain async functions wrapped by `asyncHandler`, so a thrown `AppError` (or anything else) lands in the error handler without try/catch in every handler.

Formatting is prettier (`npm run format`, `npm run format:check`); settings in `.prettierrc` and `.editorconfig`.
